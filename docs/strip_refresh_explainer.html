How rotating strip refresh works

A walkthrough of the network we cache, what we tested so far, and a frame-by-frame simulation of periodic refresh vs. refreshing one strip per frame.

1 · What we tested vs. what comes next

Our testbed is ReFrame's image-composition benchmark

This is not a diffusion model. In ReFrame and in our test, a "step" is one video frame passing through the network once. Diffusion only matters to us as the source of related caching ideas (EVO, dLLM-Cache, ToCa).

4 · What we insert

One change inside ReFrame's forward pass

ReFrame decides once per frame whether to rerun the whole deep path. We replace that decision with a small piece of the deep path on every frame. The head and the rest of the network stay the same.

ReFrame: refresh everything every N frames
# runs once per frame
if frame % N == 0:
    cache = deep_path(frame)   # slow: 77% of work
out = head(cache, frame)
Ours: refresh one strip every frame
# runs once per frame
k = frame % G                  # which strip
rows = strip(k) + border       # a few extra rows
cache[strip k] = deep_path(frame[rows])
out = head(cache, frame)       # unchanged

In our script this is the strips policy in split_refresh_test.py. Priority rotation would change only the first line: pick the strip that changed most instead of frame % G.

5 · Next tests

Find the best way to divide the refresh work

We showed that even strips flatten the spikes. Next we test how to divide the work: where to cut, which parts matter most, and how to give those parts more refreshes. One rule never changes: no full-refresh frames, and every frame gets the same refresh budget.

Three ways to schedule the same refresh work

Each square is one strip (row) in one frame (column). Orange = recomputed that frame. The bars under each grid show that frame's cost. Illustrative: the middle strips are assumed to change fastest, as when an object moves through the center of the view.

dLLM-Cache and ToCa refresh the important parts first, but they still fall back to a full refresh every few steps, so the spikes stay (middle grid). We keep their idea of favoring important parts and drop the full refresh: one strip per frame, chosen by importance, with a rule that no strip waits longer than K frames (bottom grid).

Order of work

  1. Read the papers' code. How EVO computes its importance priors (prepare_importance in its repo), how dLLM-Cache picks tokens, how they test what matters.
  2. Measure importance on our benchmark. Run the image-composition network uncached and record how much each strip and block changes frame to frame.
  3. Compare cuts. Rows, tiles, channels, blocks: same total work, measure time per frame and FLIP.
  4. Build the scheduler. Priority rotation with a fixed per-frame budget and a max age, then try an EVO-style search with a per-frame cap.
  5. Evaluate. All schedules against ReFrame's periodic refresh on the trade-off plot: worst-case frame time vs. FLIP.
